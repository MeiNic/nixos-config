# NixOS Configuration

Personal NixOS system configuration for a Framework 13 laptop with an Intel Core Ultra 155H (Meteor Lake), running **KDE Plasma 6**. Channel-based (`nixos-26.05`, plus `nixos-unstable` for a few fast-moving packages), no flake.

---

## Commands

Every command lives in [COMMANDS.md](COMMANDS.md): the day-to-day ones first (rebuilds, updates, backups, diagnostics), then the one-time procedures for each topic below. This README explains what they do and why.

Updating the channels also moves claude-code (CLI + VS Code extension), joplin-desktop and zotero, which come from the `nixos-unstable` channel via the overlay in `system/nix.nix`. The two remaining hash pins (sops-nix, open-android-backup) are bumped by hand: [COMMANDS.md § Pinned versions](COMMANDS.md#pinned-versions).

## Daily Workflow

`/etc/nixos` *is* the `@configs` btrfs subvolume, mounted there directly and owned by `nico`, so all git operations work **without `sudo`**. `~/nixos-config` is a plain symlink pointing at `/etc/nixos`; either path reaches the same files.

The login shell is Fish, which has a `nixos-rebuild` abbreviation that expands to `sudo nixos-rebuild switch`. `nico` has a `NOPASSWD` sudo rule specifically for `nixos-rebuild`, so the password prompt only appears for other sudo commands.

| Graphics | Intel Arc/Xe with VAAPI (`intel-media-driver`), 32-bit support for Wine |

| Firmware updates | `fwupd` enabled, `enableAllFirmware` |
| YubiKey / Smart-card | `pcscd` enabled (in `security/auth.nix`) |

### LUKS Sensitive Values

`system/boot.nix` reads the `shared` partition's LUKS UUID from `secrets/luks-uuids.nix` (gitignored). Copy `secrets/luks-uuids.nix.template` to `secrets/luks-uuids.nix` and fill in your own value from `blkid` output. The `crypt_nixos` UUID is not kept here — it comes from the auto-generated `hardware-configuration.nix`.

## Filesystems (`system/filesystems.nix`)

The root filesystem is its own btrfs on `crypt_nixos` (defined in `hardware-configuration.nix`). Everything else lives as subvolumes on the **shared LUKS partition** (`/dev/mapper/shared`, btrfs), all mounted with `compress=zstd` and `noatime`:

| Mount Point | btrfs Subvolume | Notes |
|---|---|---|
| `/nix` | `@nix` | Nix store |
| `/home` | `@home` | User home directories |
| `/etc/nixos` | `@configs` | This repo — git-managed, owned by `nico` |
| `/var/lib/docker` | `@docker` | Docker data (`data-root = /var/lib/docker`, btrfs storage driver) |
| `/var/lib/flatpak` | `@flatpak` | Flatpak apps |
| `/.snapshots` | `@snapshots` | btrbk snapshot target (see `backup/snapshots.nix`) |

The same file enables NTFS support (`ntfs-3g`).

> **Important:** VS Code or your file manager may show `/etc/nixos` as a mountable/unmountable volume — **do not unmount it while the system is running**. It *is* the config repo, and `~/nixos-config` points at it.

|---|---|

### Keys to place manually (not managed by Nix)

In `~/.ssh/`:
- `gh_action_key` + `gh_action_key.pub` — GitHub push/pull auth
- `git_signing_key` + `git_signing_key.pub` — Git commit signing (add the `.pub` to GitHub → Settings → SSH keys → Signing keys)

In `~/` (migration from Windows):
- `my_public_key.asc` + `my_secret_key.asc` — GPG key for Thunderbird OpenPGP

The GPG key has capabilities `[SC]` (primary) + `[E]` (subkey). The `[E]` subkey is used by Thunderbird for email encryption — Git commit signing uses SSH instead. Import it for Thunderbird once: [COMMANDS.md § GPG key import](COMMANDS.md#gpg-key-import).

## Backup (`backup/`)

Three independent layers: local snapshots, an offsite Borg repo, and a second Borg repo on a USB hard drive. The Android phone backup is a separate pipeline (see § Android Backup).

### Layer 1 — btrfs Snapshots (`backup/snapshots.nix`, local, always active)

- **Tool:** btrbk (`btrbk.service` + hourly `btrbk.timer`, `Persistent=true`)
- **Location:** `/.snapshots/` (`@snapshots` subvolume)
- **Retention:** at least 2 h, then 24 hourly / 14 daily / 8 weekly / 12 monthly
- **Subvolumes snapshotted:** `@home`, `@configs` — not the root filesystem, and not `@nix`, `@docker` or `@flatpak` (all rebuildable; snapshots would only keep garbage-collected store paths, stale Docker metadata and old Flatpak runtimes on disk)

### Layers 2 + 3 — Borg to the Storage Box and to the USB drive (`backup/borg.nix`, `backup/borg-job.sh`)

Replaces the old Vorta setup. Everything is declared in the config; nothing is configured in a GUI. Two jobs run the same script (same paths, excludes, retention and checks) into two independent repos:

| | `offsite-backup` | `usb-backup` |
|---|---|---|
| **Target** | Own Hetzner Storage Box sub-account (name in gitignored `secrets/personal.nix` → `offsiteStorageBoxUser`), repo `./borg-repo`, `--remote-path borg-1.4` | `borg-repo/` on the `backup` partition (btrfs, not LUKS) of the external 1 TB drive, found by UUID (`usbDevice`). Mounted at `/mnt/backup-hdd` only while the job runs |
| **Runs when** | AC power **and** a wired (ethernet) NetworkManager device is connected | AC power **and** the drive is connected |
| **Started by** | `offsite-backup.timer` (every 10 min) | `usb-backup.timer` (every 10 min), and right away when the drive is plugged in |
| **Extra secrets** | `offsite-backup-ssh-key` in `secrets.yaml`; host key pinned in `secrets/hetzner-storagebox-known_hosts` | — |

Common to both:

| | |
|---|---|
| **Encryption** | `repokey-blake2`. One passphrase for both repos (each has its own key): `offsite-backup-passphrase` in `secrets.yaml` (sops) |
| **When** | A start does nothing unless the last success is >24 h old (or a run is unfinished), the last failure is >1 h old, and the job's conditions hold |
| **Pause / resume** | The script re-checks the conditions every 5 s. If they stop holding it stops borg (SIGTERM, progress up to the last 3-min checkpoint stays in the repo) and exits cleanly; the next start that passes resumes the same archive. Pulling the USB drive mid-run is a pause, not a failure |
| **Sleep** | Suspend is inhibited while a job runs |
| **Notifications** | Desktop notification on success (USB: the drive is unmounted and can be unplugged), on failure, and — low urgency — on pause. Via the user's session bus; silently skipped if nobody is logged in |
| **Retention** | 7 daily, 4 weekly, 6 monthly; `borg compact` afterwards |
| **Integrity** | Every 30 days, after a successful backup: `borg check --repository-only` (Storage Box: runs server-side, nothing is downloaded; USB: reads the repo once). It runs before the success notification. Problems → failure notification. Interrupted checks are retried after the next backup; `backup-status` shows the last pass |

| Included | Excluded |
|---|---|
| `/home/nico`, `/etc/nixos` (with gitignored `secrets/`), `/var/lib/sops-nix` (the age key) | Build output at any depth (`node_modules`, `__pycache__`, `.venv`, `.gradle`, `.dart_tool`, Cargo `target/` via `CACHEDIR.TAG`, …), browser/Electron caches, `~/.cache`, `~/.cargo/registry`, `~/.rustup`, `~/.npm`, `~/.vscode/extensions`, Android SDK/AVDs, Trash, the rclone mounts. Any directory containing a `.nobackup` file is skipped too |

The exact list is `backup/borg-excludes.txt`. Wine/Affinity prefixes and the `~/wine` installers are **excluded** (their Documents/Desktop/Pictures/Downloads are symlinks into `~`, so user files are still covered; Affinity settings in the prefix's `AppData` are not). `~/Applications` is **included**.

#### One-time setup — offsite

Five steps — a dedicated SSH key, installed on the sub-account, key + passphrase in `secrets.yaml`, the passphrase saved in a password manager, rebuild: [COMMANDS.md § Borg offsite setup](COMMANDS.md#borg-offsite-setup).

#### One-time setup — USB drive

Nothing to do besides plugging it in: the repo is created on the first run. One constraint: borg refuses to create a repo *inside* another one, so the partition root must not be a borg repo itself. The old Vorta repo that sat there was deleted before the first run. For a different drive: create a btrfs partition, put its UUID into `usbDevice` in `settings.nix`, rebuild, plug it in.

#### Key export (both repos)

Both repos are initialised automatically on their first run. Afterwards, export each repo key once and store it next to the passphrase. In `repokey` mode the key lives inside the repo; the export (itself passphrase-protected) is the fallback if that part of the repo is ever damaged: [COMMANDS.md § Borg key export](COMMANDS.md#borg-key-export).

#### Daily use

Status, manual runs, forcing a fresh backup, and browsing/restoring from either repo: [COMMANDS.md § Borg daily use](COMMANDS.md#borg-daily-use).

#### Disaster recovery (laptop lost)

You need the repo passphrase (password manager), plus either the USB drive or the sub-account password. From the drive: mount the `backup` partition on any Linux machine with borg 1.4 and `borg list` / `borg extract` its `borg-repo/`. From the Storage Box: generate a new key, install it with `install-ssh-key`, point `BORG_RSH` at it, and `borg list` / `borg extract` as above. `/var/lib/sops-nix/key.txt` and `/etc/nixos/secrets/` are inside the archives (`var/lib/sops-nix`, `etc/nixos`).

## Android Backup (`backup/android.nix`)

Backs up the phone (unrooted, no `adb backup`) to a Hetzner Storage Box.

**Pipeline:** [open-android-backup](https://github.com/mrrfv/open-android-backup) (vendored via `fetchFromGitHub`, pinned to `v1.2.3`) creates a password-encrypted, 7z-compressed archive on this machine (APKs, internal storage, and — manual run only — contacts as vCards) → `rclone` uploads it to the Storage Box over SFTP → the local copy is deleted after the upload and the remote is pruned to the last 5 archives.

### Two services, because contacts need a human

| Service | Trigger | Contents |
|---|---|---|
| `android-backup-auto` | udev rule, fires when the phone's ADB interface appears over USB (plug in and walk away) | Apps + internal storage |
| `android-backup-manual` | `sudo systemctl start android-backup-manual` | Apps + internal storage + **contacts** |

Contacts aren't in the automatic run because open-android-backup's companion app has no unattended mode for contacts export — it needs a physical tap of "Export Data" on the phone's screen. Worse, if `backup_contacts=yes` and nobody's there to tap it, the upstream script hard-exits, aborting the *entire* backup (apps and storage too). So the udev-triggered path deliberately skips contacts (and skips installing the companion app altogether via `CI=1`, since it's only needed for contacts); run the manual unit yourself when you want contacts included and are standing at the phone.

### The udev rule

Matches the standard Android ADB USB interface (class `ff` / subclass `42` / protocol `01`) rather than a vendor ID, so it fires for any Android phone with USB debugging on.

### Excluding photos

`DCIM` and `Pictures` are dropped from the local staging area before compression via open-android-backup's supported `backup_hook` extension point (`use_hooks=yes` + a generated `hooks.sh`).

### Upstream patch

`backup/open-android-backup-nixos-unattended-fixes.patch`, four fixes against the pinned `v1.2.3`, all found by actually running the vendored script end-to-end (against a stub `adb`) rather than trusting a successful `nixos-rebuild build` alone:

1. **Whiptail checklist has no `-v` guard.** Unlike every other interactive prompt in `backup_func.sh`, the "what to back up" checklist has no guard for `backup_apps`/`backup_storage`/`backup_contacts` being pre-set — it would block forever on a TTY-less systemd service even with every documented unattended-mode env var set. Guarded it the same way the rest of the script is.
2. **Low-space check swallowed by `set -e`.** `enough_free_space` is called bare, so its non-zero return kills the script under `set -e` before the friendly "not enough space" message can print — a bare `exit 1` with no explanation. Capturing the status with `|| fs_status=$?` keeps the intended error path reachable.
3. **`PLEASE_READ.txt` fails to write.** `extras/backup_archive_info.txt` is vendored into the read-only Nix store, so `cp` (which carries over source permissions for a newly-created destination) leaves the staged copy mode 444. The following `echo >>` append then fails with "Permission denied." Restored the write bit right after the copy.
4. **Archives were silently encrypted with an empty password (security-critical).** Upstream feeds `archive_password` to 7z's *interactive* double-prompt over a one-line stdin pipe (`-p < <(echo "$archive_password")`), silently producing an archive encrypted with an **empty password** instead of the real one. Switched to 7z's documented non-interactive `-p<password>` flag, which sidesteps the prompt entirely. Trade-off: the password is then briefly visible in that process's argv (e.g. to other root-equivalent users via `ps`) instead of only over a pipe — an acceptable trade for the archive actually being encrypted with the intended password. Re-verified across repeated runs after the fix: correct password required, empty password rejected.

### Hetzner Storage Box (one time)

The Robot panel didn't offer an "add SSH key" option for this sub-account. Hetzner's docs (docs.hetzner.com/de/storage/storage-box/backup-space-ssh-keys) cover exactly this: Storage Boxes accept key installation over SSH itself via a built-in `install-ssh-key` command on port 23, and it explicitly works for sub-accounts too — no Robot UI needed.

The sub-account's name goes into `androidStorageBoxUser` in the gitignored `secrets/personal.nix` (the repo is public); `<android-sub-account>` in the commands stands for it. Five steps — a dedicated SSH key pair, installed on the sub-account, the private key into `secrets.yaml`, the pinned host key (verify the fingerprint against Robot's panel!), the archive password: [COMMANDS.md § Android backup setup](COMMANDS.md#android-backup-setup).

### One-time phone setup

- Enable Developer Options → USB Debugging on the phone.
- Plug it in once, run either service by hand, and tap "Always allow from this computer" on the phone's authorization prompt. After that, `~/.android/adbkey` (nico's, reused by both services via `HOME=/home/nico`) is already trusted — no more prompts. `/home` is a persistent `@home` subvolume in this config (no impermanence), so the key survives rebuilds without any extra handling.

### Useful commands

Trigger the full backup, watch it run, list what's on the Storage Box: [COMMANDS.md § Android backup](COMMANDS.md#android-backup).

### Failure visibility

No alerting pattern (e.g. ntfy/apprise/mail) exists elsewhere in this config, so this doesn't invent one — failures surface as a failed systemd unit and journal output only (`systemctl status android-backup-auto`). (`backup/borg.nix` is the one exception: it sends desktop notifications itself.)

## Secrets

Two tiers, by whether Nix needs the *value* at eval/build time or a service just needs a *file path* at runtime.

### Real secrets → sops-nix (`security/secrets.nix`, `secrets.yaml`)

Actual passphrases and keys live encrypted in `secrets.yaml`, tracked in git. Encryption is [age](https://github.com/FiloSottile/age) (X25519 + ChaCha20-Poly1305) — sops itself always encrypts values with AES256-GCM regardless of key backend; age is what protects the wrapping key, and was chosen over GPG for its far smaller attack surface. `.sops.yaml` at the repo root declares which age public key(s) can decrypt it.

The one piece of key material that can't live in git — by definition, since it's what protects everything that does — is the age *private* key, at `/var/lib/sops-nix/key.txt` (root:root, 0400). **Back this up somewhere deliberate** (password manager, printed recovery sheet); losing it means losing every secret in `secrets.yaml` with no recovery path. It was generated once with `age-keygen` and is not itself in git.

At system activation, `sops-install-secrets` decrypts `secrets.yaml` into `/run/secrets/<name>` — tmpfs, RAM-only, recreated fresh every boot. Modules reference `config.sops.secrets.<name>.path` instead of a hardcoded file path:

| Secret | Consumer | Permissions |
|---|---|---|
| `u2f-mappings` | `security/auth.nix` (`security.pam.u2f.settings.authfile`) | root:root 0444 — PAM needs to read it outside a pure root context |
| `android-backup-env` | `backup/android.nix` (systemd `EnvironmentFile=`) | root:root 0400 (default) |
| `hetzner-storagebox-key` | `backup/android.nix` (`rclone --sftp-key-file`) | root:root 0400 (default) |
| `offsite-backup-passphrase` | `backup/borg.nix` (`BORG_PASSCOMMAND`, both repos) | root:root 0400 (default) |
| `offsite-backup-ssh-key` | `backup/borg.nix` (`BORG_RSH`, Storage Box repo) | root:root 0400 (default) |

**Editing a secret** (interactively, or scripted from a file): [COMMANDS.md § Secrets](COMMANDS.md#secrets).

The `sudo env SOPS_AGE_KEY_FILE=...` is required every time: the plain `sops` CLI's own key lookup (`~/.config/sops/age/keys.txt` by default) is independent of the `sops.age.keyFile` NixOS option, which only governs decryption during system activation — not interactive CLI use. And note `/run/wrappers/bin/sudo` is the actual setuid binary if bare `sudo` ever resolves to the unwrapped one from a script's PATH.

To add a brand new secret: add its key via `sops set`, then declare it in `security/secrets.nix` (`sops.secrets.<name> = { };`, override `owner`/`mode` only if the default root:root 0400 doesn't suit the consumer), then reference `config.sops.secrets.<name>.path` from the consuming module.

### Values needed at eval time, or not actually secret → plain files (`secrets/`)

The `secrets/` directory is gitignored (except `*.template` files). These can't be sops secrets even in principle — sops only produces runtime file paths, and these get spliced into Nix-evaluated config or are needed before sops can even run. A fresh checkout needs each template copied to its real name and filled in before `nixos-rebuild` will evaluate.

| File | Purpose |
|---|---|
| `personal.nix` | Git name, email, SSH signing public key (loaded by `security/git-ssh.nix`, baked into a generated `/etc/ssh/allowed_signers` at build time) and the Storage Box sub-account names (loaded by `backup/borg.nix` and `backup/android.nix`) — not sensitive, just kept out of the public repo |
| `luks-uuids.nix` | LUKS UUID of the `shared` partition (loaded by `system/boot.nix`) — needed in initrd, long before sops could decrypt anything |
| `eduroam.nix` | eduroam EAP identity and home RADIUS server pin (loaded by `system/networking.nix`) — spliced into a NetworkManager profile at build time |
| `hetzner-storagebox-known_hosts` | Pinned SFTP host key for the Storage Box — not actually secret (SSH host keys are public; pinning is for integrity, not confidentiality), just never got promoted out of this directory |

## Security & Authentication (`security/auth.nix`)

The lock screen enforces **YubiKey (PIV) _or_ password + fingerprint**. The fingerprint is only ever a **second factor** — never sufficient on its own, on *any* surface — because the Linux fingerprint stack isn't trusted as a sole credential.

### How Plasma 6 drives the lock screen

Plasma runs three PAM services **in parallel** and unlocks on the first that succeeds — so multi-factor policy is expressed by what each service allows, not by one combined stack:

| PAM service | Method | Configured as |
|---|---|---|
| `kde` | password | password **AND** fingerprint, chained, with faillock |
| `kde-fingerprint` | fingerprint alone | **denied** — a swipe by itself never unlocks |
| `kde-smartcard` | YubiKey PIV / PKCS#11 | `pam_p11` → `opensc-pkcs11.so`, YubiKey-only (no password) |

Effective lock-screen policy: **YubiKey PIV PIN**, or **password → fingerprint**.

### Everywhere else (sudo, su, TTY login, polkit, sshd)

Accepts **password or YubiKey** (PIV PIN, or U2F touch) — fingerprint is **not** offered. This is enforced by running the fprintd daemon *without* `services.fprintd.enable` (also in `security/auth.nix`): that option would otherwise flip NixOS's `fprintAuth` default on and add the fingerprint as a sole factor to every PAM service.

### Authentication methods

| Method | Mechanism | Used for |
|---|---|---|
| YubiKey FIDO2 | systemd initrd, `fido2-device=auto` (`system/boot.nix`) | LUKS boot unlock of both devices |
| YubiKey U2F | `pam_u2f` | sudo, TTY login (`u2f-mappings` in `secrets.yaml`, see § Secrets) |
| YubiKey PIV/PKCS#11 | `pam_p11` | lock-screen smartcard unlock; also accepted for sudo/login (`~/.eid/authorized_certificates`) |
| Password + fingerprint | `pam_unix` + `pam_fprintd` | lock-screen fallback — both required, in sequence |

### Kernel session keyring

NixOS doesn't add `pam_keyinit` anywhere by default, so sessions never got a proper kernel session keyring and keyutils-backed tools (e.g. `proton-pass-cli`'s credential store) failed with `EACCES`. `security/auth.nix` adds `pam_keyinit force revoke` to the `login` (TTY and SDDM) and `systemd-user` services.

### Account lockout & recovery

`pam_faillock` on the lock screen: **2 failures** (bad password *or* bad swipe, either order) → locked, `unlock_time=0` (no auto-expiry). Check and reset it with `faillock`: [COMMANDS.md § Security and authentication](COMMANDS.md#security-and-authentication).

While locked, the rescue paths are the **YubiKey PIV** (on the lock screen itself) or a **TTY password login** (`Ctrl+Alt+F2`).

### YubiKey PIV enrollment (lock-screen smartcard method)

Each key holds its own PIV key + self-signed cert in slot `9a`; `pam_p11` authorizes any cert listed in `~/.eid/authorized_certificates`. Provision **each** key (plug in only one at a time): [COMMANDS.md § YubiKey PIV enrollment](COMMANDS.md#yubikey-piv-enrollment).

Verify: `ykman piv info` shows a cert in slot 9a, and `~/.eid/authorized_certificates` holds one `BEGIN CERTIFICATE` block per key.

### YubiKey U2F enrollment (sudo / TTY)

The mapping file is the `u2f-mappings` entry in `secrets.yaml` (see § Secrets — one line per key, sops-encrypted). To add a key, generate its line and paste it in via the interactive editor: [COMMANDS.md § YubiKey U2F enrollment](COMMANDS.md#yubikey-u2f-enrollment).

### Emergency access

`login` (TTY, `Ctrl+Alt+F2`) accepts your password, so you can always drop to a console, log in as `nico` and reset the lockout ([COMMANDS.md § Security and authentication](COMMANDS.md#security-and-authentication)).

Or select the **previous NixOS generation** at the systemd-boot menu during boot; the old auth config still works.

## eduroam (`system/networking.nix`)

Connects to eduroam using a client certificate (EAP-TLS) instead of a username and password. Works at any eduroam campus worldwide — authentication is always routed back to the home institution's RADIUS server via the identity realm in the certificate.

### Setup

**1. Get your client certificate** as a `.p12` file from your institution:
- DFN/easyroam: [easyroam.eduroam.de](https://easyroam.eduroam.de)
- Other institutions: look for the eduroam CAT or geteduroam portal

The commands for steps 2–4 are in [COMMANDS.md § eduroam setup](COMMANDS.md#eduroam-setup).

**2. Extract cert and key** into `certs/` (gitignored): the public client certificate, and the private key unencrypted (mode 400, owned by wpa_supplicant via tmpfiles).

> `-legacy` is required for older RC2-encrypted `.p12` files (easyroam uses this format). Put your `.p12` password after `pass:`, or leave it empty if there is none.

**3. Fill in your secrets:** copy `secrets/eduroam.nix.template` to `secrets/eduroam.nix`, then set:

| Value | What it is |
|---|---|
| `identity` | The CN from your cert |
| `domainSuffixMatch` | Server name(s) your supplicant sees (in the `wpa_supplicant` journal) — use the parent domain(s). DFN/easyroam users typically need `your-uni.de;eduroam.de`. |

**4. Rebuild.**

eduroam will connect automatically whenever it is in range.

### Certificate Renewal

The easyroam certificate expires after ~1 year. Renew it at the easyroam portal and re-run step 2 above to replace the files in `certs/`. The rest of the config stays the same.

## Affinity on Linux (`desktop/affinity.nix`)

Runs **Affinity by Canva** (free, 3.x) and **Affinity v2** via Wine (requires Wine >= 10.17, we use stable 11.0+). Wine can't be built declaratively (it downloads .NET, builds a mutable prefix), so the setup is imperative but reproducible via helper scripts. The module also provides the system-wide `wine` on PATH, so the installer step runs the same build that created the prefix.

### Setup (one time)

Five steps — create the wine prefix, run the installer, apply the WineFix (Affinity by Canva only), install DXVK, launch: [COMMANDS.md § Affinity setup](COMMANDS.md#affinity-setup).

### Display Scaling

Wine doesn't detect per-monitor KDE scaling on X11/Wayland. Set it manually with `affinity-scale <percent>`: [COMMANDS.md § Affinity display scaling](COMMANDS.md#affinity-display-scaling).
