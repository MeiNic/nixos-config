# NixOS Configuration

Personal NixOS system configuration for a laptop with an Intel Core Ultra 155H (Meteor Lake), running **KDE Plasma 6**.

## Frequently Used Commands

### Configuration Management

```bash
# Edit config and apply changes to the system
cd ~/nixos-config
git add -A && git commit -m "feat: describe change"
sudo nixos-rebuild switch      # Apply changes (fish abbreviation: nixos-rebuild)

# Test changes without making them the default boot entry
sudo nixos-rebuild test

# Build without applying
sudo nixos-rebuild build

# Git operations (no sudo needed)
git add -A && git commit -m "..."
git push
```

### System Updates & Maintenance

```bash
# Update nixpkgs channel (pulls latest stable packages)
sudo nix-channel --update

# Apply updates and rebuild
sudo nixos-rebuild switch --upgrade

# Clean up old generations and free disk space
sudo nix-collect-garbage            # Remove unreachable packages
sudo nix-collect-garbage -d         # Also remove older generations

# Check current NixOS/Nix versions
nixos-version
nix --version

# List all available NixOS generations (for rollback)
sudo nixos-rebuild list-generations

# Boot into a previous generation at next reboot
sudo nixos-rebuild switch --rollback

# Check service status
sudo systemctl status
```

### Backup & Snapshot Management

```bash
# Check backup status
sudo systemctl status borgbackup-job-usb-a
sudo systemctl status borgbackup-job-usb-manual

# Manually trigger USB Drive A backup
sudo systemctl start borgbackup-job-usb-a

# Manually trigger USB Drive B backup (manual drive)
sudo systemctl start borgbackup-job-usb-manual

# Check btrfs snapshot status
sudo btrfs subvolume list /

# List backup archives
sudo BORG_PASSPHRASE=$(cat /etc/nixos/secrets/borg-passphrase) \
  borg list /mnt/borg-usb-a/borg-repo

# Android → Hetzner Storage Box (auto-fires on USB connect; run manually for contacts)
sudo systemctl start android-backup-manual
sudo journalctl -fu android-backup-auto
```

## Daily Workflow

The `@configs` btrfs subvolume is mounted at `~/nixos-config` (owned by `nico`), so all git operations work **without `sudo`**. `/etc/nixos` is a symlink pointing to `~/nixos-config`, which is re-created on every rebuild by an activation script.

The login shell is Fish, which has a `nixos-rebuild` abbreviation that expands to `sudo nixos-rebuild switch`. `nico` has a `NOPASSWD` sudo rule specifically for `nixos-rebuild`, so the password prompt only appears for other sudo commands.


## Backup (`backup.nix`)

A two-layer backup strategy:

### Layer 1 — btrfs Snapshots (local)

- **Tool:** btrbk
- **Location:** `/.snapshots/` (`@snapshots` subvolume)
- **Schedule:** Hourly (keep 24h) + daily at midnight (keep 14d / 8w / 12m)
- **Subvolumes snapshotted:** root, `@home`, `@configs`, `@nix`, `@docker`, `@flatpak`

### Layer 2 — BorgBackup to USB Drive A (automatic)

- **Timer:** daily at 02:30 (`Persistent=true` — catches up after missed runs)
- **Drive absent:** exits cleanly, no failure logged
- **Compression:** `auto,zstd`
- **Checkpointing:** every 5 minutes (interrupted backups resume)

### Layer 3 — BorgBackup to USB Drive B (manual)

- **No timer** — triggered manually only
  ```bash
  sudo systemctl start borgbackup-job-usb-manual
  ```

### What is Backed Up

| Included | Excluded |
|---|---|
| `/home`, `/etc/nixos`, `/var/lib/docker`, `/var/lib/flatpak` | `/.cache`, `__pycache__`, `.npm`, `.cargo/registry`, `.rustup`, Trash, `docker/overlay2` |

### USB Drive Setup (one time per drive)

```bash
# 1. Format and label the partition
sudo mkfs.ext4 -L borg-usb-a /dev/sdX1
sudo mkfs.ext4 -L borg-usb-b /dev/sdX1

# 2. Create mount points
sudo mkdir -p /mnt/borg-usb-a /mnt/borg-usb-b

# 3. Initialise Borg repositories (drive must be plugged in)
export BORG_PASSPHRASE="your-strong-passphrase"
sudo borg init --encryption=repokey-blake2 /mnt/borg-usb-a/borg-repo
sudo borg init --encryption=repokey-blake2 /mnt/borg-usb-b/borg-repo

# 4. Store the passphrase
sudo mkdir -p /etc/nixos/secrets
echo "your-strong-passphrase" | sudo tee /etc/nixos/secrets/borg-passphrase
sudo chmod 600 /etc/nixos/secrets/borg-passphrase
```

> **Not currently set up on this machine** — this USB-drive layer is superseded by a separate Vorta-managed Borg backup outside this config. `secrets/borg-passphrase` doesn't exist, so `borgbackup-job-usb-a`/`-manual` will fail until it's created per the steps above.

### Useful Backup Commands

```bash
# Check last backup status
sudo systemctl status borgbackup-job-usb-a
sudo systemctl status borgbackup-job-usb-manual

# List archives on a drive
sudo BORG_PASSPHRASE=$(cat /etc/nixos/secrets/borg-passphrase) \
  borg list /mnt/borg-usb-a/borg-repo

# Restore a specific file
sudo BORG_PASSPHRASE=$(cat /etc/nixos/secrets/borg-passphrase) \
  borg extract /mnt/borg-usb-a/borg-repo::archive-name path/to/file
```

## Android Backup (`android-backup.nix`)

Backs up the phone (unrooted, no `adb backup`) to a Hetzner Storage Box.

**Pipeline:** [open-android-backup](https://github.com/mrrfv/open-android-backup) (vendored via `fetchFromGitHub`, pinned to `v1.2.3`) creates a password-encrypted, 7z-compressed archive on this machine (APKs, internal storage, and — manual run only — contacts as vCards) → `rclone` uploads it to the Storage Box over SFTP → the local copy is deleted after the upload and the remote is pruned to the last 5 archives.

### Two services, because contacts need a human

| Service | Trigger | Contents |
|---|---|---|
| `android-backup-auto` | udev rule, fires when the phone's ADB interface appears over USB (plug in and walk away) | Apps + internal storage |
| `android-backup-manual` | `sudo systemctl start android-backup-manual` | Apps + internal storage + **contacts** |

Contacts aren't in the automatic run because open-android-backup's companion app has no unattended mode for contacts export — it needs a physical tap of "Export Data" on the phone's screen. Worse, if `backup_contacts=yes` and nobody's there to tap it, the upstream script hard-exits, aborting the *entire* backup (apps and storage too). So the udev-triggered path deliberately skips contacts (and skips installing the companion app altogether via `CI=1`, since it's only needed for contacts); run the manual unit yourself when you want contacts included and are standing at the phone.

### The udev rule

Matches the standard Android ADB USB interface (class `ff` / subclass `42` / protocol `01`) rather than a vendor ID, so it fires for any Android phone with USB debugging on.

### Excluding photos

`DCIM` and `Pictures` are dropped from the local staging area before compression via open-android-backup's supported `backup_hook` extension point (`use_hooks=yes` + a generated `hooks.sh`).

### Upstream patch

`patches/open-android-backup-nixos-unattended-fixes.patch`, three fixes against the pinned commit, all found by actually running the vendored script end-to-end (against a stub `adb`) rather than trusting a successful `nixos-rebuild build` alone:

1. **Whiptail checklist has no `-v` guard.** Unlike every other interactive prompt in `backup_func.sh`, the "what to back up" checklist has no guard for `backup_apps`/`backup_storage`/`backup_contacts` being pre-set — it would block forever on a TTY-less systemd service even with every documented unattended-mode env var set. Guarded it the same way the rest of the script is.
2. **`PLEASE_READ.txt` fails to write.** `extras/backup_archive_info.txt` is vendored into the read-only Nix store, so `cp` (which carries over source permissions for a newly-created destination) leaves the staged copy mode 444. The following `echo >>` append then fails with "Permission denied." Restored the write bit right after the copy.
3. **Archives were silently encrypted with an empty password (security-critical).** Upstream feeds `archive_password` to 7z's *interactive* double-prompt over a one-line stdin pipe (`-p < <(echo "$archive_password")`), silently producing an archive encrypted with an **empty password** instead of the real one. Switched to 7z's documented non-interactive `-p<password>` flag, which sidesteps the prompt entirely. Trade-off: the password is then briefly visible in that process's argv (e.g. to other root-equivalent users via `ps`) instead of only over a pipe — an acceptable trade for the archive actually being encrypted with the intended password. Re-verified across repeated runs after the fix: correct password required, empty password rejected.

### Hetzner Storage Box (one time)

The Robot panel didn't offer an "add SSH key" option for this sub-account. Hetzner's docs (docs.hetzner.com/de/storage/storage-box/backup-space-ssh-keys) cover exactly this: Storage Boxes accept key installation over SSH itself via a built-in `install-ssh-key` command on port 23, and it explicitly works for sub-accounts too — no Robot UI needed.

```bash
# 1. Generate a dedicated SSH keypair
ssh-keygen -t ed25519 -f /tmp/hetzner-storagebox -C "android-backup@nixos"

# 2. Install the public key on the sub-account via Hetzner's built-in command
#    (prompts for the sub-account's password once)
cat /tmp/hetzner-storagebox.pub | ssh -p23 u643857-sub4@u643857-sub4.your-storagebox.de install-ssh-key

# 3. Put the private key into secrets.yaml (see § Secrets for why the sudo
#    env wrapper is needed) and drop the local copies
cd /etc/nixos
sudo env SOPS_AGE_KEY_FILE=/var/lib/sops-nix/key.txt sops set secrets.yaml \
  '["hetzner-storagebox-key"]' "$(cat /tmp/hetzner-storagebox | nix-shell -p jq --run 'jq -Rs .')"
rm /tmp/hetzner-storagebox /tmp/hetzner-storagebox.pub

# 4. Pin the SFTP host key (verify the fingerprint against Robot's panel!)
#    Not a secret - stays a plain file, unlike the key above.
ssh-keyscan -p 23 u643857-sub4.your-storagebox.de | sudo tee /etc/nixos/secrets/hetzner-storagebox-known_hosts
sudo chown root:root /etc/nixos/secrets/hetzner-storagebox-known_hosts
sudo chmod 600 /etc/nixos/secrets/hetzner-storagebox-known_hosts

# 5. Set the archive password
sudo env SOPS_AGE_KEY_FILE=/var/lib/sops-nix/key.txt sops set secrets.yaml \
  '["android-backup-env"]' "$(printf 'archive_password=%s' 'your-strong-passphrase' | nix-shell -p jq --run 'jq -Rs .')"
```

### One-time phone setup

- Enable Developer Options → USB Debugging on the phone.
- Plug it in once, run either service by hand, and tap "Always allow from this computer" on the phone's authorization prompt. After that, `~/.android/adbkey` (nico's, reused by both services via `HOME=/home/nico`) is already trusted — no more prompts. `/home` is a persistent `@home` subvolume in this config (no impermanence), so the key survives rebuilds without any extra handling.

### Useful commands

```bash
# Trigger the full backup (incl. contacts) manually
sudo systemctl start android-backup-manual

# Watch it run
sudo journalctl -fu android-backup-auto
sudo journalctl -fu android-backup-manual

# List what's currently on the Storage Box
sudo rclone lsf ":sftp:android-backup" --sftp-host u643857-sub4.your-storagebox.de \
  --sftp-port 23 --sftp-user u643857-sub4 \
  --sftp-key-file /run/secrets/hetzner-storagebox-key \
  --sftp-known-hosts-file /etc/nixos/secrets/hetzner-storagebox-known_hosts \
  --sftp-shell-type unix
```

### Failure visibility

No alerting pattern (e.g. ntfy/apprise/mail) exists elsewhere in this config, so this doesn't invent one — failures surface as a failed systemd unit and journal output only (`systemctl status android-backup-auto`). `borgmatic` (installed for the USB-drive backups in `backup.nix`) pulls in `apprise` as a dependency already, if you want to wire up notifications later.

## Secrets

Two tiers, by whether Nix needs the *value* at eval/build time or a service just needs a *file path* at runtime.

### Real secrets → sops-nix (`secrets.nix`, `secrets.yaml`)

Actual passphrases and keys live encrypted in `secrets.yaml`, tracked in git. Encryption is [age](https://github.com/FiloSottile/age) (X25519 + ChaCha20-Poly1305) — sops itself always encrypts values with AES256-GCM regardless of key backend; age is what protects the wrapping key, and was chosen over GPG for its far smaller attack surface. `.sops.yaml` at the repo root declares which age public key(s) can decrypt it.

The one piece of key material that can't live in git — by definition, since it's what protects everything that does — is the age *private* key, at `/var/lib/sops-nix/key.txt` (root:root, 0400). **Back this up somewhere deliberate** (password manager, printed recovery sheet); losing it means losing every secret in `secrets.yaml` with no recovery path. It was generated once with `age-keygen` and is not itself in git.

At system activation, `sops-install-secrets` decrypts `secrets.yaml` into `/run/secrets/<name>` — tmpfs, RAM-only, recreated fresh every boot. Modules reference `config.sops.secrets.<name>.path` instead of a hardcoded file path:

| Secret | Consumer | Permissions |
|---|---|---|
| `u2f-mappings` | `security-auth.nix` (`security.pam.u2f.settings.authfile`) | root:root 0444 — PAM needs to read it outside a pure root context |
| `android-backup-env` | `android-backup.nix` (systemd `EnvironmentFile=`) | root:root 0400 (default) |
| `hetzner-storagebox-key` | `android-backup.nix` (`rclone --sftp-key-file`) | root:root 0400 (default) |

**Editing a secret:**

```bash
# Interactive (decrypts to $EDITOR, re-encrypts on save) - simplest for one-off edits
sudo env SOPS_AGE_KEY_FILE=/var/lib/sops-nix/key.txt sops secrets.yaml

# Scripted / from a file, preserving exact byte content (multi-line keys etc.)
sudo env SOPS_AGE_KEY_FILE=/var/lib/sops-nix/key.txt sops set secrets.yaml \
  '["secret-name"]' "$(sudo cat /path/to/file | nix-shell -p jq --run 'jq -Rs .')"
```

The `sudo env SOPS_AGE_KEY_FILE=...` is required every time: the plain `sops` CLI's own key lookup (`~/.config/sops/age/keys.txt` by default) is independent of the `sops.age.keyFile` NixOS option, which only governs decryption during system activation — not interactive CLI use. And note `/run/wrappers/bin/sudo` is the actual setuid binary if bare `sudo` ever resolves to the unwrapped one from a script's PATH.

To add a brand new secret: add its key via `sops set` above, then declare it in `secrets.nix` (`sops.secrets.<name> = { };`, override `owner`/`mode` only if the default root:root 0400 doesn't suit the consumer), then reference `config.sops.secrets.<name>.path` from the consuming module.

### Values needed at eval time, or not actually secret → plain files (`secrets/`)

The `secrets/` directory is gitignored (except `*.template` files). These can't be sops secrets even in principle — sops only produces runtime file paths, and these get spliced into Nix-evaluated config or are needed before sops can even run:

| File | Purpose |
|---|---|

## Security & Authentication (`security-auth.nix`)

The lock screen enforces **YubiKey (PIV) _or_ password + fingerprint**. The fingerprint is only ever a **second factor** — never sufficient on its own, on *any* surface — because the Linux fingerprint stack isn't trusted as a sole credential.

### How Plasma 6 drives the lock screen

Plasma runs three PAM services **in parallel** and unlocks on the first that succeeds — so multi-factor policy is expressed by what each service allows, not by one combined stack:

| PAM service | Method | Configured as |
|---|---|---|
| `kde` | password | password **AND** fingerprint, chained, with faillock |
| `kde-fingerprint` | fingerprint alone | **denied** — a swipe by itself never unlocks |
| `kde-smartcard` | YubiKey PIV / PKCS#11 | `pam_p11` → `opensc-pkcs11.so`, YubiKey-only (no password) |

Effective lock-screen policy: **YubiKey PIV PIN**, or **password → fingerprint**.

### Everywhere else (sudo, su, TTY login, polkit, sshd)

Accepts **password or YubiKey** (PIV PIN, or U2F touch) — fingerprint is **not** offered. This is enforced by running the fprintd daemon *without* `services.fprintd.enable` (see `desktop.nix`): that option would otherwise flip NixOS's `fprintAuth` default on and add the fingerprint as a sole factor to every PAM service.

### Authentication methods

| Method | Module | Used for |
|---|---|---|
| YubiKey FIDO2/U2F | `pam_u2f` | LUKS boot unlock, sudo, TTY login (`u2f-mappings` in `secrets.yaml`, see § Secrets) |
| YubiKey PIV/PKCS#11 | `pam_p11` | lock-screen smartcard unlock; also accepted for sudo/login (`~/.eid/authorized_certificates`) |
| Password + fingerprint | `pam_unix` + `pam_fprintd` | lock-screen fallback — both required, in sequence |

### Account lockout & recovery

`pam_faillock` on the lock screen: **2 failures** (bad password *or* bad swipe, either order) → locked, `unlock_time=0` (no auto-expiry).

```bash
faillock --user nico            # check lock status
faillock --user nico --reset    # unlock (sudo still works via YubiKey)
```

While locked, the rescue paths are the **YubiKey PIV** (on the lock screen itself) or a **TTY password login** (`Ctrl+Alt+F2`).

### YubiKey PIV enrollment (lock-screen smartcard method)

Each key holds its own PIV key + self-signed cert in slot `9a`; `pam_p11` authorizes any cert listed in `~/.eid/authorized_certificates`. Provision **each** key (plug in only one at a time):

```bash
ykman piv access change-management-key --generate --protect  # replace factory default
ykman piv access change-pin        # default 123456 → yours (6–8 digits)
ykman piv access change-puk        # default 12345678 → yours
ykman piv keys generate --algorithm eccp384 9a ~/piv-pub.pem
ykman piv certificates generate --subject "CN=nico-piv-<name>" 9a ~/piv-pub.pem
mkdir -p ~/.eid && chmod 700 ~/.eid
ykman piv certificates export 9a - >> ~/.eid/authorized_certificates   # APPEND — one block per key
chmod 600 ~/.eid/authorized_certificates && rm ~/piv-pub.pem
```

Verify: `ykman piv info` shows a cert in slot 9a, and `~/.eid/authorized_certificates` holds one `BEGIN CERTIFICATE` block per key.

### YubiKey FIDO2/U2F enrollment (sudo / boot / TTY)

The mapping file is the `u2f-mappings` entry in `secrets.yaml` (see § Secrets — one line per key, sops-encrypted). To add a key, generate its line and paste it in via the interactive editor:

```bash
pamu2fcfg -n   # -n if u2f-mappings already has a key in it, otherwise omit
sudo env SOPS_AGE_KEY_FILE=/var/lib/sops-nix/key.txt sops secrets.yaml   # append the line above under u2f-mappings, save
```

### Emergency access

`login` (TTY, `Ctrl+Alt+F2`) accepts your password, so you can always drop to a console and unlock:

```bash
# Ctrl+Alt+F2 → login: nico → password
faillock --user nico --reset
```

Or select the **previous NixOS generation** at the systemd-boot menu during boot; the old auth config still works.

## eduroam (`eduroam.nix`)

Connects to eduroam using a client certificate (EAP-TLS) instead of a username and password. Works at any eduroam campus worldwide — authentication is always routed back to the home institution's RADIUS server via the identity realm in the certificate.

### Setup

**1. Get your client certificate** as a `.p12` file from your institution:
- DFN/easyroam: [easyroam.eduroam.de](https://easyroam.eduroam.de)
- Other institutions: look for the eduroam CAT or geteduroam portal

**2. Extract cert and key** into `certs/` (gitignored):

```bash
mkdir -p /etc/nixos/certs

# Public client certificate
openssl pkcs12 -legacy -in YOUR.p12 -clcerts -nokeys -passin pass: \
  | openssl x509 -out /etc/nixos/certs/eduroam-client.pem

# Unencrypted private key (mode 400, owned by wpa_supplicant via tmpfiles)
openssl pkcs12 -legacy -in YOUR.p12 -nocerts -nodes -passin pass: \
  | openssl pkey -out /etc/nixos/certs/eduroam-key.pem
```

> `-legacy` is required for older RC2-encrypted `.p12` files (easyroam uses this format). Put your `.p12` password after `pass:`, or leave it empty if there is none.

**3. Fill in your secrets:**

```bash
cp secrets/eduroam.nix.template secrets/eduroam.nix
```

Then edit `secrets/eduroam.nix`:

| Value | How to find it |
|---|---|
| `identity` | CN from your cert: `openssl x509 -in certs/eduroam-client.pem -noout -subject` |
| `domainSuffixMatch` | Server name(s) your supplicant sees: `journalctl -u wpa_supplicant \| grep 'PEER-CERT depth=0'` — use the parent domain(s). DFN/easyroam users typically need `your-uni.de;eduroam.de`. |

**4. Rebuild:**

```bash
sudo nixos-rebuild switch
```

eduroam will connect automatically whenever it is in range.

### Certificate Renewal

The easyroam certificate expires after ~1 year. Renew it at the easyroam portal and re-run step 2 above to replace the files in `certs/`. The rest of the config stays the same.

## Affinity on Linux (`affinity.nix`)

Runs **Affinity by Canva** (free, 3.x) and **Affinity v2** via Wine (requires Wine >= 10.17, we use stable 11.0+). Wine can't be built declaratively (it downloads .NET, builds a mutable prefix), so the setup is imperative but reproducible via helper scripts.

### Setup (one time)

```bash
# 1. Create and configure the wine prefix
affinity-setup                 # Takes 10-20 min (downloads .NET 4.8)

# 2. Download and run the installer
# Affinity by Canva: https://www.affinity.studio/download
# Affinity v2: https://affinity.serif.com/v2/
WINEPREFIX=$HOME/.affinity wine ~/Downloads/'Affinity x64.exe'

# 3. For Affinity by Canva only — apply the WineFix (patches sign-in + prefs saving)
affinity-winefix

# 4. Launch
affinity                       # Launches Affinity by Canva
affinity Photo                 # Launches Affinity v2 Photo (or Designer/Publisher)
```

### Display Scaling

Wine doesn't detect per-monitor KDE scaling on X11/Wayland. Set it manually:

```bash
affinity-scale 135             # 135% scale → 130 DPI
affinity-scale 150             # 150% scale → 144 DPI
affinity-scale 170             # 170% scale → 163 DPI
```
